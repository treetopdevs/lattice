## Verdicts

**Slice 2A (journal foundation): PASS — no P0/P1/P2.** The packet is implementable as specified, faithful to the adopted contract, and claims no custody. Three P3 observations below.

**Slice 2B (provider/protected bridge) design: NOT PASS as written — one P2.** The Rust-side conservative signing-TTL rule, as worded, silently makes any native review longer than roughly 60 seconds unable to release a signature, contradicting the adopted 120-second review + 60-second signing contract, and each such failure permanently burns one of the 4,096 lifetime validator nonces. ## P2 (2B only) — §5, Rust release-deadline anchor makes valid slow reviews structurally impossible

**Where:** Proposal §5, the paragraph beginning "Consent inserts the globally unique validator nonce durably…": *"Rust's release check must conservatively use the same deadline via a remaining duration captured before the prepare response is sent (subtract transit time using its own request-start monotonic bound), never grant a new 60s on receipt."*

**Why it's a defect:** The only Rust monotonic instant that precedes Kotlin's capture of the remaining duration is the start of the `prove_binding`/prepare request. Anchoring there yields an effective Rust deadline of `prepare_request_start + remaining`, where `remaining ≤ 60s` — but the native review (adopted limit 120s) happens *between* request start and consent. Concretely: review takes 90s (valid), user authenticates 10s after consent (valid — Kotlin's own consent-anchored checks all pass), signature is produced; then Rust's final release check sees ~100s elapsed against a ~60s budget and refuses. The validator nonce was durably spent at consent and is never deleted, so every retry of a careful reviewer burns another of the 4,096 lifetime nonces while presenting as a generic post-authentication failure. The "never grant a new 60s on receipt" half is correct (no deadline reset); the transit-subtraction half over-corrects by the entire review duration.

**Repro (design-level):** Trace the proposal's own mermaid sequence in §5 with review time = 90s, presence time = 10s: every Kotlin boundary check ("before opening presence, after blocking presence, after `sign()`, before every release") passes against the consent-anchored 60s deadline; the Rust release check, computed as specified, has already expired ~30s before `sign()` completes. Note the B03 gate as written would not catch this: its timeout cases assert that expired attempts release nothing, and this behavior *is* a refusal — the tests would go green around a broken adopted flow.

**Exact fix:** Keep Kotlin's retained consent deadline authoritative at every blocking boundary (already specified). For Rust's independent envelope, anchor at a Rust-observed instant that cannot precede consent — the monotonic instant Rust receives the private prepare response (consent strictly precedes response send), or the observed `treehouse:witness-pending-v1` phase transition to `presence`. State explicitly that (a) Rust's check is a defense-in-depth upper envelope of `receive_instant + remaining`, loose only by in-process transit, never an extension of Kotlin's deadline, which remains the enforced one; (b) review time is never subtracted from the signing window and the deadline is never re-derived on any later receipt; and (c) a Rust-envelope refusal after platform signing is still terminal (no signature release, nonce stays spent), matching the existing one-shot rule.

## P3 observations (non-blocking)

- Two Kotlin citations are slightly off: `BindingCodec.kt:11–25` is actually 10–24, and the pilot assertions cited as `BindingCodecTest.kt:24–25` sit at 22–23. All other ~20 line citations I checked were exact.
- The 2A return types `Snapshot`/`ConsentRecord`/`GenerationFence` are defined by implication from the schema table rather than enumerated; harmless for a tests-only storage layer, but enumerating their fields in the 2A packet would remove one degree of implementer freedom.
- A05's two-JVM lock contention requires `WitnessProcessLock` to be loadable in a plain JVM without Android classes; the proposed pure `FileChannel.tryLock` design permits this, worth preserving deliberately during implementation.

**Bottom line:** authorize 2A as proposed — nothing in the unimplemented 2B or in unresolved physical facts blocks it. For 2B, adopt the design only after amending the §5 Rust deadline anchor as above; everything else in the 2B packet (numeric-byte transport, pending-event cancellation ownership, drain task, per-use CryptoObject flow, alias absence/error/certificate-only distinctions, the 0/-1 KeyInfo handling, and the honest non-claims) is grounded in the sources I checked.
