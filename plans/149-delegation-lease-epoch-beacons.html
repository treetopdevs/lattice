Plan 149 — Delegation Leases via Epoch Beacons

Bounded-lifetime capabilities for Lattice.Authority — classical, deterministic, log-native. No wall clocks, no new cryptography.

Track: substrate (plans/)  ·  Extends: Lattice.Authority / Lattice.Authority.Delegation  ·  Follows: 147 (TS capability & revocation validation), 144–146 (succession hardening)  ·  Status: implemented on pd003/toolshed (2026-07-18) — steps 1–7 green locally (V1–V7, V9; V8 via workflows test); awaiting hosted closure + merge

Objective

Today a 2.0 delegation is immortal. The Lattice.Authority.Delegation struct carries {id, replica, issuer, audience, parent_id, ops, roles, live, sig} and nothing else — the only way authorization ever ends is an explicit {:revoke, delegation_id} op, and revocation only bites where the news propagates. A holder who takes a grant and never syncs again holds it forever, and any partition that never receives the revoke keeps accepting their ops indefinitely.

This plan adds leases: a delegation may carry an expiry expressed in epochs, and the replica root publishes signed beacon ops that advance the epoch on the log itself. When a beacon passes a delegation's expiry, ops citing that delegation are quarantined — by exactly the same causal judgment the codebase already uses for revocation. The burden of liveness inverts: today the issuer must be online to revoke; with leases the holder must reconnect to renew, which is the right default for a civic instance.

Done means: a delegation granted with expires_epoch: 3 stops authorizing new ops once a valid beacon with epoch > 3 exists in the log, deterministically on every replica, with byte-identical replay preserved (G2), the TypeScript client reaching the same verdicts from the same pinned oracle vectors, and every existing delegation, vector, and signature still valid untouched.

Scope honesty Expiry bounds acceptance of new ops by others — the only thing the authority model ever controlled. It cannot retract data a holder already replicated, and it cannot stop them writing to their own local log. Both are inherent to local-first, not defects of this design.

Design in one picture

Why this shape

The G2 exit gate requires convergence and byte-identical replay: materialization must be a deterministic function of log content. That rules out wall-clock expiry outright — two replicas reading the same log at different times must not disagree. The only admissible notion of "now" is something on the log, and the codebase already has two such devices:

  • Causal revocation — revoked_as_of?/5 (authority.ex:784): an op is quarantined :revoked_capability iff a valid revoke of its cited delegation (or any link of its chain) exists that the op is not causally before.
  • Logical ticks — role timelines already carry at_tick heartbeats and dormancy-based succession (decide_heartbeat/4, last_active_from/3).

Leases compose the two: a beacon op is a root-signed tick that is content on the log, and lease lapse is a derived revocation triggered by it. Because the judgment mirrors revoked_as_of? exactly, the convergence argument is the one already proven for revocation — replicas with different logs may disagree transiently and converge as logs converge, and quarantine is recomputed per materialization, never stored.

Decision — division of labor with succession Leases govern delegation-cited command capability (the cap_ok/7 path). Serialized-authority roles already have a liveness mechanism — heartbeats, dormancy, and succession ... after: {:dormant_ticks, n} — and this plan does not duplicate it. One liveness story per authority kind.
Accepted trade — fail-open toward availability Nothing lapses until the root actually publishes a beacon past the expiry epoch. If the root goes silent, leases outlive their intent. The alternative — lapse by local clock — breaks determinism and is rejected. Root beacon cadence is an operational concern (see Open Questions); a partitioned clique that includes the root keeps advancing, and one that doesn't degrades exactly as it does today, no worse.

Hard-to-reverse decisions (pinned now)

DecisionChoiceRationale
Wire format New canonical arm "lattice-delegation-v3" used only when expires_epoch is set; unleased delegations keep the existing "lattice-delegation-v2" bytes verbatim. Delegation ids are content hashes and signatures cover the encoding (Lattice.Canonical.delegation_bytes/7, mirrored by canonicalBytesForCarrierDelegation in clients/lattice-client/src/codec.ts). Reusing v2 for the nil case means every existing id, signature, persisted log, and pinned oracle vector remains byte-identical — the back-compat proof is "regenerate vectors, diff is empty".
Expiry unit expires_epoch :: non_neg_integer | nil — the last epoch in which the delegation authorizes ops. nil = no lease (today's behavior). Epochs are log-native and coarse by design. Fine-grained lifetimes are the issuer's cadence choice, not a new time base.
Beacon op :authority kind, body {:beacon, epoch}, valid only from the replica root (resolved by the existing resolve_root/4), and only when epoch is strictly greater than every valid beacon epoch in the op's causal ancestry. Mirrors revoke authorization ("issuer or replica root") in its strictest form; monotonicity-in-ancestry makes beacon validity itself a pure causal judgment. Violations quarantine as :unauthorized_beacon / :stale_beacon, modeled on unauthorized_revokes/3.
Lapse judgment Op O citing delegation chain C is quarantined :lease_expired iff some link d ∈ C has expires_epoch = E ≠ nil and a valid beacon B with B.epoch > E exists that O is not causally before. Character-for-character the revoked_as_of? shape: same ancestor sets, same chain walk, same convergence proof, same replay stability (an op accepted before the beacon stays accepted — it is causally before it).
Attenuation attenuates?/2 gains: child's effective expiry must not exceed the parent's (nil = unbounded; a child of a leased parent must carry expires_epoch ≤ parent's). Otherwise delegation launders a lease away. Checked per-link, like the existing subset rules for ops/roles/live.
Renewal No new op type. Renewal = issuer signs a fresh delegation with a later expires_epoch (new content-addressed id); the holder cites the new id going forward. Delegations stay immutable and content-addressed; an in-place {:renew, id, epoch} op would break the id ≡ hash(encoding) invariant that valid_sig?/1 and the TS client both rely on.

Where it plugs into analyze/2

The core judgment, next to its template

Existing — revoked_as_of?/5 (authority.ex:784)

# Op O is revoked-as-of iff a valid revoke of
# its delegation (or its chain) exists that O
# is not causally before.
defp revoked_as_of?(op, deleg, delegations,
                    revokes, ancestors) do
  chain_ids(deleg, delegations)
  |> Enum.any?(fn id ->
    case Map.get(revokes, id) do
      nil -> false
      revoke_op ->
        not MapSet.member?(
          Map.get(ancestors, revoke_op, MapSet.new()),
          op.id)
    end
  end)
end

New — expired_as_of?/5 (planned shape)

# Op O is lease-expired iff some chain link has
# expires_epoch E and a valid beacon with
# epoch > E exists that O is not causally before.
defp expired_as_of?(op, deleg, delegations,
                    beacons, ancestors) do
  chain_links(deleg, delegations)
  |> Enum.any?(fn %Delegation{expires_epoch: e} ->
    e != nil and
      Enum.any?(beacons, fn %{epoch: be, op_id: bid} ->
        be > e and
          not MapSet.member?(
            Map.get(ancestors, bid, MapSet.new()),
            op.id)
      end)
  end)
end

Explicitly out of scope

  • No wall-clock anywhere in the judgment. The v1 runtime Lattice.Cap ttl_ms/expires_at fields stay as they are (Gateway session hygiene); bridging them onto epochs is a possible follow-up, not this plan.
  • No beacon scheduler. Cadence is driven by tests/Sim/operators for now; a supervised periodic beacon process is an app-layer follow-up.
  • No role-timeline expiry. Roles keep dormancy + succession (plans 144–146) as their liveness story.
  • No grace-period policy. Grace is folded into the issuer's choice of expires_epoch; a per-replica policies: hook can come later without wire changes.
  • No quorum beacons, no ZK, no election changes. Multi-signer beacons belong with M6 federation questions; privacy of chains and non-revocation proofs are the separate ZK track; Township.Election and the frozen Lattice.Attestation.Stub are untouched.

Risks

RiskMitigation
Elixir/TS canonical drift on the v3 bytes — the classic cross-realm failure mode. The five new pinned vectors are generated by the Elixir oracle and asserted by TS conformance; the v2 path is proven unchanged by the empty regeneration diff.
Accidental invalidation of existing logs/vectors via the encoding change. Nil-lease delegations never touch the v3 arm; step 6's byte-identical regeneration check is a hard gate.
Quarantine-reason precedence churn (an op both revoked and lease-expired flapping between reasons across replicas). Fixed evaluation order inside cap_ok (visibility → grant scope → revoked → expired), asserted by a dedicated test with an op that is both.
Beacon spam or forged epochs distorting lapse. Root-only authorship + strict monotonicity-in-ancestry; invalid beacons are quarantined for audit and confer no lapse (mirrors forged-authority handling from the Round-3 V-01 remediation).
Interaction with witnessed succession (plans 145/146). Leases never touch role timelines by design; the adversarial suite in apps/lattice_stress/test/adversarial_authority_test.exs runs unmodified as a regression gate.

Open Questions

Defaults are marked; the plan proceeds on them unless overridden.

Q1 — Who may author beacons?

a) Replica root only (recommended) — strictest, mirrors revoke authority, smallest surface for the first cut.
b) Root or a designated role holder (e.g. a :steward role) — more operationally flexible, but couples leases to role timelines on day one.

Q2 — Beacon cadence ownership?

a) Manual / test-driven for this plan (recommended) — cadence is Sim- and operator-driven; the substrate stays policy-free.
b) Ship a supervised beacon GenServer now — convenient, but it drags scheduling policy into the substrate track prematurely.

Q3 — Should delegation_active?/2 lapse the live Gateway path in this plan, or append-path only first?

a) Both paths together (recommended) — design invariant 2 says one chain, two uses; splitting them invites a window where live messaging outlives append authority.
b) Append path first, live path as follow-up — smaller diff, temporary inconsistency accepted.

Q4 — Default lease on new grants?

a) No default — leases are opt-in per grant (recommended) — zero behavior change for existing callers; Township chooses leases explicitly where the scenario wants them.
b) Default all new grants to a lease — safer posture eventually, but a breaking behavior change for every existing test and caller, better taken as its own migration plan.
