§ 01Thesis

Everywhere else in Lattice, zero-knowledge proofs are an optimization: they compress a delegation-chain lookup, they make an audit log verifiable, they shrink a state sync. In the M4 election path, ZK is not an optimization. It is the only known mechanism that can deliver the properties the roadmap demands — eligibility without identity, one vote per election without linkability, and a tally whose correctness anyone can check without anyone being able to prove how they voted.

The repo already knows this. CLAUDE.md names three blocking conditions for Township.Election: anonymous ingress, private registration, and the pinned cryptographic construction. Every security claim in the implemented foundation is frozen at not claimed until those gates clear. Nothing else on the Lattice ZK menu — capability SNARKs, MMR log commitments, verifiable state sync — changes a claim state. This path does. That is the argument for spending the deep-study budget here.

The finding of this investigation is that the 2024–2026 toolchain covers the gates unevenly, and the unevenness is the useful result. Semaphore-style membership nullifiers and IETF-track BBS credentials are mature enough to prototype the eligibility and registration layers now, behind the existing Township.Election.Protocol seam. The tally layer — CHide-family encrypted cleansing — is specified, peer-reviewed, and implementable, but its measured cost at town scale is the open question that gate 13 exists to answer. And a specific class of problems (close finality, artifact availability, transport metadata) is not a ZK problem at all, and no amount of proving will move it.

The shape of what already exists is worth being precise about, because it is exactly the substrate a ZK profile plugs into. Township.Election.verify_link/3 binds an immutable ElectionSpec digest to an authorized Matter-side {:link_election, [spec_digest]} op, then derives the election ID as a domain-separated hash of both — so any change to choices, roles, keys, thresholds, or profile produces a new election. Township.ElectionBoard is a separate capability-gated replica whose command surface (:submit_ballot, :publish_box_seal, :certify_close, :publish_protocol_artifact, :publish_tally…) lets Lattice.Authority validate the outer publisher while a pure projector validates the inner protocol. Phase is derived from verified certificates, never from an LWW field. Projection is total, set-based, and byte-identical across arrival permutations.

What is deliberately absent is everything cryptographic: no credential scheme, no anonymous channel, no DKG, no proof system, no trustee runners. Those are gates 2–8. This document maps the current toolchain onto them.

§ 03Why the old seam died — and what it teaches the ZK design

The retired interface asked for four callbacks: cast_vouch/3, tally/2, produce_alt/2, receipt_free?/0. The verdict's core argument is short enough to restate whole, because every design decision downstream inherits from it. The interface required a public deterministic singleton tally, an immutable signed logged body, and an "alternative" body that counts for a different choice. Those three requirements hand the coercer a perfect distinguisher:

  1. Read the target's logged body. Run the public tally/2 on it — the choice is revealed with probability 1.
  2. When shown an alternative body, byte-compare it against the log. If it differs, Lattice.Op's content hash and Ed25519 signature expose the substitution; if it is identical, determinism forces the same tally.

The second lesson is the one that matters most for the ZK layer: JCJ-family coercion resistance has inverted semantics from what the old API assumed. The coerced artifact is not a second body that counts differently — it is a ballot cast under a fake credential that looks perfectly valid on the public board and is silently excluded during encrypted cleansing. The coerced vote must not count, and no observer — including the coercer holding everything the voter surrendered — may be able to tell which ballots were removed. The legacy contract literally asserted the opposite (tally([alt]) counting the demanded choice), which would let a coercer change election results.

Five falsifying properties from the verdict become standing constraints on any ZK profile:

  • A public deterministic plaintext tally is a choice oracle — the deterministic Lattice operation must be verify_finalized_tally(transcript), never decrypt_and_tally(bodies).
  • Content-addressed ops make byte-different alternatives detectable — deniability must live inside the ciphertext, not in the log.
  • Byte-identical alternatives cannot tally differently — same reason.
  • Fake evidence must be excluded, not counted — encrypted cleansing, not body substitution.
  • Outer author/cap/deps metadata makes participation observable — the voter must never author the public ballot op with an ordinary Lattice.Identity. An anonymous box or relay authors the outer op; the encrypted inner ballot carries no Lattice identity.
Standing ruleBallots and credentials never touch Township.Matter. The Matter log stores only the authorized election-link command; the board stores service-authored public artifacts. Constraint five is why the "anonymous ingress" gate exists at all.

§ 04The redesigned protocol surface

The replacement architecture is a multi-role, multi-phase election protocol in which Lattice supplies exactly four things: an immutable bulletin board, capability-gated service publication, replication, and deterministic replay. Everything cryptographic hides behind one deliberately small facade:

Township.Election
  → client ballot and decoy preparation          # prepare_ballot/4, make_decoy/3
  → role-state advancement                       # advance/3 — registrar, box, close, trustees
  → pure board projection and verification       # verify/3 — total, set-based, non-networked
  → structured security claims                   # claims/1 — reviewed static manifest

Township.ElectionBoard
  → capability-gated append-only artifacts
  → no voter identities, no materialized plaintext tally

Four private seams sit behind the facade — Protocol (the one pinned construction), AnonymousTransport (with a deterministic test adapter and a separately assessed real adapter), ArtifactStore (content-addressed bytes and offline bundles), and the role runners. The brief is explicit that construction internals — CHide's Setup, Vote, Check, isVal, Fakecred, Ptally, Verify — must not leak upward as a growing pile of application callbacks. This is the seam every ZK library evaluated below must fit behind.

Roles, and what a capability does not prove

Nine roles are frozen into the election configuration: matter sponsor, supervisor, registration tellers, voter client, ballot boxes, close committee, tally trustees, auditors, and the Lattice replica/carrier itself. The trust boundary the brief draws is the sharpest sentence in it: a Lattice capability proves that a service may publish an artifact family. It does not prove credential validity, anonymous eligibility, private delivery, honest thresholds, correct client behavior, complete delivery, or a non-equivocating close. Those are exactly the properties the ZK layer and the operational design must supply — which is why capabilities and proofs are complements here, not substitutes.

Close finality: the deliberately conservative choice

A CRDT frontier cannot fix a canonical ballot set — eventual delivery has no globally complete view. The POC policy is :unanimous_boxes_v1: every configured ballot box signs exactly one seal naming every wrapper it accepted, all boxes co-sign one union manifest, and the close certificate carries every signature. Uniqueness holds if a single box is honest; the price is liveness — one withholding box leaves the election :pending. Competing valid certificates mean :forked_close, and the projector must never break the tie by hash, topology, author, or arrival time. If unanimity proves operationally unacceptable, the named replacement is a separately proven BFT close service — not Lattice ordering. Keep this section in mind at §12: no proof system fixes it.

§ 05Gate: private registration → anonymous credentials

conditional — toolchain mature

Registration must deliver each eligible voter a private credential, publish only encrypted credential material to the roster, and satisfy an honest-party assumption over the registration tellers. Two credential families from the 2024–2026 toolchain apply, at two different layers:

BBS signatures for the issuance layer

BBS is the anonymous-credential workhorse: a constant-size multi-message signature whose holder can generate unlinkable zero-knowledge proofs of knowledge while selectively disclosing any subset of signed attributes. It is now deep in IETF standardization — draft-irtf-cfrg-bbs-signatures-10 landed in January 2026, based on the Tessaro–Zhu 2023 security treatment — which matters for gate 12 (independent review) because a reviewed RFC-track primitive is a far smaller audit surface than a bespoke scheme. For Township, a BBS credential lets a registration teller sign (roster_epoch, eligibility_attributes, credential_commitment) once, and lets the voter later prove possession without the teller or anyone else linking the proof back to issuance. Notably, BBS proofs' hiding properties hold even against a future quantum adversary, though unforgeability does not — a reasonable posture for a civic roster.

JCJ/CHide credentials for the coercion layer

BBS alone is not coercion-resistant: a coerced voter can surrender a BBS credential, and the coercer can then vote or verify with it. The JCJ line adds the property that makes M4 hard: fake credentials indistinguishable from real ones. CHide's Fakecred(c) derives decoy material from the voter's real private credential; a ballot cast with it is publicly well-formed, survives every relay check, and is removed only inside the encrypted cleansing phase — invisibly. This is what make_decoy/3 in the Protocol behaviour encodes, and why it receives the real credential: fakes are derived, not minted independently. The registration ceremony must therefore give each voter an untappable moment — one opportunity to receive the real credential unobserved — and the designated-verifier proofs used during issuance must convince the voter without producing evidence transferable to a coercer.

LayeringBBS answers "is this holder on the roster?" unlinkably. JCJ/CHide credentials answer "does this ballot count?" deniably. The candidate profile in §08 uses both, at different points in the envelope.

§ 06Gate: anonymous ingress → nullifiers, scoped precisely

conditional — with one sharp caveat

The prompt's framing — "registered voter proves membership plus one-vote-per-election without linkability" — is exactly the Semaphore contract, and Semaphore is the most production-hardened way to get it. Semaphore v4 (PSE) is a Groth16/BN254 protocol over a Poseidon-hashed Lean Incremental Merkle Tree of identity commitments; identities are EdDSA keypairs, which makes them reusable across systems rather than trapped inside one circuit. A proof demonstrates three statements simultaneously: the prover controls a commitment in the group tree; the message (ballot-wrapper digest, here) is bound into the proof; and a nullifier — deterministically derived from the identity secret and a public scope — is well-formed. Set the scope to the election_id and the nullifier becomes a one-per-voter-per-election token that reveals nothing about which roster member produced it.

Mapped onto the board, this closes real gaps immediately:

  • Eligibility at the box. A relay accepting a :submit_ballot can require a Semaphore proof against the sealed roster tree before authoring the wrapper op — spam and non-member submissions die at ingress without the box learning who submitted. This directly serves the brief's denial-of-service boundary requirement (gate 5).
  • Roster commitment. The ElectionSpec roster commitment becomes the LeanIMT root, sealed by the registration certificate at :ready.
  • Participation privacy. The outer op author is the box; the inner proof is anonymous; nothing on the board links a ballot to a roster entry — which is the property whose absence made forced abstention observable under the old seam.

The caveat that decides the architecture

A Semaphore nullifier is publicly linkable within its scope: two submissions from the same identity under the same election_id expose the duplicate by nullifier equality. That is the feature when the policy is "strictly one signal." It is a hazard for coercion resistance, where CHide's semantics require duplicate and fake-credential ballots to remain publicly unclassified, their fate hidden inside encrypted cleansing. Two consequences:

  • If revoting is part of the evasion strategy (vote under coercion, revote freely later — the classic JCJ pattern), a naive per-election nullifier would publicly flag the revote and hand the coercer a compliance check. The nullifier scope must then be per-submission-window or omitted at the ballot layer entirely, with all duplicate resolution deferred to encrypted cleansing.
  • If the pinned profile forbids revoting, the per-election nullifier is safe for exact-duplicate suppression only — and note the board already deduplicates exact retransmissions by inner artifact digest, so the nullifier's marginal job is stopping distinct double ballots, which is precisely the case where public linkability leaks.

The honest resolution: Semaphore-style nullifiers belong at the eligibility/anti-DoS layer; the count-integrity layer's duplicate policy must live inside the pinned construction's cleansing phase. Which duplicate policy matches the security game is already logged as an open research decision in the brief (§17) — this analysis gives it a concrete shape: the nullifier scope is a profile parameter that must be pinned together with the revote policy, not chosen independently.

The surrendered-secret attack — found in adversarial review

A nullifier is deterministic from (identity_secret, scope). If the Semaphore proof is published to the board alongside the ballot wrapper, the board's nullifier set becomes a participation registry keyed by identity secrets: a coercer who demands the voter's EdDSA identity secret — the JCJ credential-surrender scenario, squarely in scope — recomputes the election-scope nullifier locally and scans the board. Participation becomes provable, resurrecting the forced-abstention channel the redesign eliminated at the op-author layer. A second cost compounds it: gating ingress on roster membership removes non-member dummy ballots, and the brief's own gate 5 and benchmark requirements name a cover/dummy policy explicitly — JCJ-family evasion leans on background traffic that anyone can generate. Three dispositions, escalating in fidelity to the theorem:

  • Box-private admission. The box verifies the proof and discards it; nothing nullifier-shaped reaches the board. This keeps DoS protection and forfeits public auditability of admission — acceptable, because ballot stuffing with fake credentials cannot change the tally, only its size. The box already sits inside the metadata trust boundary; learning a scope-pseudonym adds little to what a malicious box could already correlate.
  • Ephemeral scopes. If any nullifier must be public, scope it per submission epoch, not per election — rate limiting without an election-lifetime pseudonym. This weakens dedup to per-epoch, which is fine, because dedup was never this layer's job (§06 above).
  • No admission control at all. Vanilla CHide assumes an open-posting board. Every admission extension — including this one — is a deviation the composition argument (gate 12) must carry. Whether admission control exists, and on which side of the theorem's board model it lives, is therefore a gate 2 profile decision, not an architecture default. §14 records this as the review's highest-severity finding.

§ 07Gate: the pinned construction — CHide, priced honestly

open — cost is the blocker, not existence

The brief's target profile is a single version-pinned CHide or encrypted-sorting CHide construction (Cortier–Gaudry–Yang, ePrint 2022/430; encrypted-sorting treatment, ePrint 2023/837). The semantic shape fits the redesigned architecture exactly: trustees run a DKG for exponential ElGamal; registrars issue private credentials and publish encrypted material; voters submit encrypted (choice, credential) pairs with well-formedness proofs over an anonymous channel; encrypted equality tests, conditional zeroing, and an oblivious sort hide which fake or duplicate ballots were cleansed; anyone verifies the transcript. The coercion-resistance theorem holds under DDH with SUC-secure DKG and mixnet components in the programmable random-oracle model.

The verdict document imported the numbers that make this a gate rather than a checkbox, and they deserve to be stated plainly:

Two readings of those numbers. Pessimistic: quadratic CHide at 10k is effectively unusable on civic hardware. Realistic: the tally is trustee-side batch work, not client work — 48 CPU-days is embarrassingly parallel MPC across a trustee committee, and the encrypted-sorting variant plus 2024–2026 GPU acceleration (MSM/NTT kernels of the kind ICICLE ships) attack exactly the dominant cost. The client's cost — one ballot encryption plus proofs — is milliseconds-to-seconds and is the part §09 moves into the browser. The correct posture is the brief's: pin the encrypted-sorting profile as the candidate, then let measurement, not optimism, clear gate 13.

One alternative deserves its standing rejection restated: MACI gets invoked whenever "anti-collusion voting" comes up, and the verdict already dispatched it — the MACI coordinator holds the decryption key and processes messages off-chain, producing a ZK proof of the result. That is a trusted-coordinator model, weaker than CHide's threshold-trustee model, and it does not fit a facade whose whole point is that no single party can decrypt. The same table retired chameleon-hash commitments, Hirt–Sako channels, deniable encryption, and linkable ring signatures, each for a specific reduction failure.

#               — whether this proof is board-published, box-private, or absent is a G2 decision (§06, §14)

# It must not — and cannot — test whether the credential is real. (verdict §3)
box authors {:submit_ballot, [election_id, ballot_ref]}   # outer op: box identity + box capability

# under coercion — the decoy path; the coerced ballot is well-formed and will not count
{:ok, decoy} = Protocol.make_decoy(verified, real_credential, entropy)

The check token is the voter's opaque inclusion evidence — it verifies presence on the board without opening the choice, and it is never logged. The brief's open question about acceptance evidence creating new coercion surface (§17) applies to it directly. One structural advantage surfaced in review deserves stating: because Lattice is local-first, every participant replicates the full board, so the inclusion check is a local lookup — no distinguishing "is my ballot there?" query ever leaves the device. Centralized bulletin boards need private information retrieval to get this; Lattice gets it from its replication model for free.

Curve independenceThe stack spans three curve regimes — BN254 (Semaphore/Groth16), BLS12-381 (BBS), and the pinned profile's ElGamal group — and it works only because the layers verify independently; no cross-curve recursion is assumed anywhere. If the pinned profile ever requires binding the JCJ credential to roster membership inside one proof, non-native field arithmetic makes that binding brutally expensive, and curve unification becomes a hard gate-2 constraint. Pin the independence assumption explicitly so nobody violates it casually.

§ 09Client-side proving in the split-execution architecture

The companion Lattice ZK study already established the pattern for the constrained realm, and the election path inherits it unchanged: AtomVM computes, the host browser proves. AtomVM's WASM build has no big-integer support and no parallelism; running MSM inside it is a non-starter. The hybrid keeps the BEAM code in charge of state and protocol logic while proof generation crosses the bridge:

  1. The AtomVM realm assembles the witness — verified election context, credential secret, choice, entropy — into a shared buffer via the JS bridge.
  2. The host context runs a WebGPU-accelerated prover (ICICLE-class MSM/NTT kernels; Plonky3-class vectorized proving) and returns the proof. Semaphore's Groth16 circuit is small — browser proving is sub-second on 2026 consumer GPUs, and single-digit seconds on CPU-WASM fallback.
  3. Verification stays cheap everywhere: pairing checks in tens of milliseconds, so relays, peers, and the Elixir server all verify without hardware assumptions.

Three election-specific rules tighten the generic pattern:

  • Entropy discipline splits into two opposite regimes — corrected in adversarial review. Role runners persist randomized contribution bytes before publication, so a restart republishes identical bytes for the same (election, role, phase, round). The first draft of this document extended that rule to the voter client. That was wrong, and dangerously so: persisted ballot randomness plus the known plaintext is a transferable receipt — exactly the artifact a coercer demands. The voter regime is inverted: persist the ciphertext, securely erase the randomness the moment the envelope is constructed. A retry resubmits the persisted bytes; it never regenerates. The receipt-freeness of an ElGamal ballot depends on the encryption randomness being unrecoverable, including from the device.
  • The witness crosses into the host realm — trust accordingly. The split architecture hands the JS host context the full witness: credential secret, choice, entropy. A compromised host page, a hostile extension, or bridge diagnostics that log payloads all see it. Minimum posture: prove inside a dedicated cross-origin-isolated worker, zero the shared buffer after handoff, and keep the bridge's debug surface witness-blind. The stronger answer already exists in this repo: Plans 129–131 built native key custody and secure-store handling into the packaged Tauri app, with Phoenix structurally unable to receive keys or signatures. The Tauri app is the correct high-assurance voter client; the browser tab realm is the low-assurance fallback — the election profile should say so rather than treating the two as equivalent.
  • Prover delegation is nearly closed here. The generic architecture allows outsourcing proving to a coprocessor network under encryption. For ballots, the witness is the credential and the choice — delegating it means trusting the delegate with exactly what the protocol exists to protect. Low-end devices should fall back to slow local CPU proving, not to a remote prover, unless a future profile pins a construction with a proven blind-proving mode.
  • Secret hygiene is a test contract, not a habit. The brief's secret-handling suite requires that no credential, ballot randomness, real/decoy label, or trustee share ever appears in logs, wire frames, dumps, telemetry, exceptions, or audit bundles (gate 10). The bridge buffer is in scope: zero it after witness handoff, and keep bridge diagnostics away from witness payloads.

§ 10BEAM-side integration

The server and peer replicas need verification, canonicalization, and role-runner orchestration — not proving. That division keeps the Elixir surface small:

  • Verify-only NIFs. :crypto binds OpenSSL, which has no pairing-friendly curves. A Rustler NIF wrapping arkworks (ark-groth16/BN254 for Semaphore proofs, ark-bls12-381 for BBS) exposes verify(vk, proof, public_inputs) and nothing else. Verification runs in tens of milliseconds — safe on dirty schedulers, no port program needed. Proving stays out of the BEAM entirely.
  • Canonical bytes are a cross-runtime gate. Gate 9 pins artifact codecs, bounds, and domain separation, and the conformance suite requires BEAM, native, and browser runtimes to agree on canonical bytes and verifier results. The board already restricts public artifacts to Lattice.Canonical-supported primitive terms encoded through a pinned byte codec before hashing — the ZK layer's proofs, ciphertexts, and verification keys enter the same ArtifactRef discipline: digest, byte size, codec, profile.
  • Role runners are OTP-shaped. Registrar, box, close, and trustee runners are the durable processes behind advance/3 — persisted role state, explicit effects, idempotent redelivery. This is where Lattice's actual strengths (supervision, replay, capability-gated publication) carry the protocol's operational load. Trustee replacement, however, is a construction-defined resharing ceremony; ordinary Lattice succession explicitly cannot substitute for it.
  • Toolchain. Latest-stable Elixir/OTP and Phoenix LiveView per the repo's own preference; the read-oriented township_web instrument observes projections and claim manifests, and never touches a secret — the five-panel LiveView surface renders phase, verification status, claim-set ID, and explicit non-claims, replacing the retired receipt_free? boolean.

§ 12What ZK does not solve — the honest residue

The brief's non-goals section is the best defense the project has against overclaiming, and the ZK layer changes none of it:

  • Close finality. Lattice has no global finality; the unanimous-box certificate buys uniqueness by sacrificing liveness, and its replacement is a proven BFT service. Proofs verify a fixed ballot set; they cannot fix one.
  • Transport metadata — on both legs. Naming Tor or Nym is not an anonymity claim. Forced-abstention resistance stays not claimed until a concrete transport, metadata model, cover policy, and composition proof exist. And the second leg is a channel too: the box publishes wrappers onto the carrier, and op arrival timing on a replicated board correlates with submission timing for an observer watching both the voter and the board. Boxes must publish in randomized, fixed-interval batches — a mitigation the traffic-observer model of gate 5 has to cover explicitly.
  • Everlasting privacy is not provided — and Lattice makes the failure permanent. Exponential-ElGamal ballot ciphertexts sit on an immutable, replicated board forever. A future adversary who breaks the discrete log — or simply runs a cryptographically relevant quantum computer — decrypts every ballot of every past election retroactively. BBS proofs are quantum-hiding; the ballot ciphertexts are not. On a deletable centralized board this is harvest-now-decrypt-later; on a local-first replicated log it is harvest-by-design, because deletion is structurally impossible. Everlasting privacy (perfectly hiding commitments with computationally binding openings) is a known e-voting research axis the pinned profile must at least take a position on, even if the position is an explicit non-claim.
  • The deterministic transport adapter can manufacture false confidence. A seeded test adapter makes every downstream contract green while the property that matters — unlinkability — is untested and untestable in ExUnit. The claim manifest must bind transport-dependent claims to the adapter identity, not to the AnonymousTransport seam: green with the test adapter proves protocol correctness, never anonymity.
  • Ideal-result leakage. A small or unanimous electorate reveals individual choices through the tally itself, with zero transcript leakage. At town scale — school-board wards, single-street questions — this is not an edge case, and product language must not hide it.
  • Availability and censorship. A withholding box, a vanished artifact host, a selectively dropped submission — all outside every theorem in the stack. The claims stay :not_claimed.
  • Compromised endpoints and physical surveillance. No protocol survives a coercer watching the screen or owning the client. The evasion strategy needs an unobserved moment; that is an assumption, stated as one.
  • Trusted setup residue. Groth16 (Semaphore's system) requires a per-circuit ceremony; Semaphore's is done and public, but any custom ballot circuit on Groth16 inherits a new ceremony obligation. A transparent system (Halo2/Plonky3-class) trades that for larger proofs — a profile decision to make once, at gate 2, with eyes open.

§ 13Recommended sequence

The brief's closing line already names the next authorized work: a decision/spike package for gates 2–7 — not an implementation, not a receipt_free? == true test. Concretely, in order:

  1. Write the profile pin proposal (G2). Encrypted-sorting CHide, exact revision, parameter set, transcript codec, DKG and mixnet component choices, proof-system decision (ceremony vs. transparent), and the nullifier-scope / revote-policy pairing from §06 resolved as one decision.
  2. Land the deterministic AnonymousTransport test adapter. It is already a named seam; a seeded, replayable adapter lets every downstream contract run before any real channel is assessed, and keeps the real-adapter assessment (G5) from blocking protocol work.
  3. Spike Semaphore v4 behind the Protocol seam — as a substrate rehearsal, not an architecture commitment. Roster tree as the spec's roster commitment; proof verification through the Rustler NIF; box-private admission checking (never board-published nullifiers, per the §06 surrendered-secret finding); browser proving over the existing bridge. This exercises G4/G5/G9/G10 machinery with production-hardened crypto while claiming nothing. Whether admission control survives into the pinned profile at all — and on which side of CHide's open-posting board model — is decided at step 1, informed by this spike, not preempted by it.
  4. Stand up the conformance-vector harness (G11). Semaphore and BBS vectors first; structure it so CHide vectors drop in when the profile pins.
  5. Build the G13 benchmark harness early — against the reference algorithms. Production role runners do not exist yet and are not needed: a single-process simulation of the trustee rounds from the pinned paper's reference algorithms prices the dominant cost. 100 / 1,000 / 10,000 synthetic-participant runs reporting CPU, wall time, memory, network and artifact bytes, cold/warm verification — parameterized by trustee count, candidates, dummies, revotes. If encrypted-sorting CHide fails the town-scale test in simulation, it fails cheaper there than after the runners exist.
  6. Only then: role runners, review, migration (F2 → F3 → F4). Registrar/box/close/trustee runners with durable randomness; independent review of implementation and composition; and W4 switches last, retiring M4Placeholder, the frozen Stub, and the legacy contract in the final commit of the path.
PostureEvery step above is compatible with the standing rule that the runtime claim set remains :research / :not_claimed. The work converts an unpriceable property into a priced one; the claims flip only when gates 1–13 say so.
