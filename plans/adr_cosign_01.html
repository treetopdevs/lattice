Co-Signed Consent

Consent as a domain-tagged signature carried inside the command body — the repo-native shape. Rev 2 is reconciled against main @ a96b3c4; the reconciliation flipped the core decision and dissolved two of the four risks Rev 1 hedged against.

RECONCILED · MAIN @ a96b3c4 EXTENDS · AUTHORITY.VALIDATE_COMMAND FIRST CONSUMER · PD-003 :CUSTODY_TRANSFER NO OP-STRUCT CHANGE · REV 1 SHAPE REJECTED JULY 2026 · PROPOSED
§1

Reconciliation Verdict

Rev 1 was drafted blind and carried a checklist (C1–C4) to falsify its assumptions. All four are now answered against main, and the honest summary is: the substrate is further along than the ADR assumed, the house already has a pattern for exactly this problem, and Rev 1's op-struct extension is rejected by evidence — it would lose co-signatures at the door of the real accept path.

§2

Decision: Consent in the Body

The co-signature is a consent signature over a domain-tagged canonical payload, carried inside the command body — so it is inside the hashed content. The op cannot exist without the consent, the id changes if the consent changes, and the accept path needs no modification because there is nothing outside the hash to merge. The shape the repo chose for us — Rev 2's core decision
Surface 1 — the request · existing inbox mechanism, zero new code
%Op{kind: :inbox,
    author: borrower_pub,
    body: {:request, "custody", %{tool: field_ref, action: :borrow}},
    ...}
Collected by Authority.analyze into the durable requests list; resolved by the current validated holder per Q-06. An unresolved or refused request is visible and timestamped — refusal-legibility lives here, exactly as PD-003 claimed, and it turns out to require nothing at all.
Surface 2 — the transfer · one new command, consent embedded
consent_payload = Canonical.term([
  "lattice-custody-consent-v1",   // domain tag, versioned like @op_tag
  replica,
  request_op_id,                    // the nonce: binds consent to ONE request
  from_pub,                         // current holder (the op's author)
  to_pub                            // recipient (the consenting signer)
])
consent_sig = Identity.sign(recipient, consent_payload)

%Op{kind: :command,
    author: from_pub,               // authority unchanged: author must pass
                                      // cap_ok + authority_ok as holder
    body: {:custody_transfer,
           [to_pub, request_op_id, consent_sig]},   // {cmd, args} house shape
    cap: ...,
    ...}                              // consent is INSIDE canonical bytes →
                                      // inside the id → inside the sig
The ceremony is therefore ordered by construction: the recipient signs the consent payload first (QR/NFC round-trip at the handoff — app layer, above the carrier); the holder embeds it, builds the op, appends. A body missing or carrying an invalid consent produces a different op id than a valid transfer ever would — the same-id hazard from C4 cannot arise.

The validity extension — one conjunct in the existing hook

validate_command/7 already quarantines commands per replica-module rules with reasoned audit events. The extension: for commands whose module declares required consent, verify consent_sig against the recomputed payload — checking the signer is the declared recipient, the from in the payload equals op.author, and request_op_id is present in the op's causal past. Failures quarantine as :missing_consent / :invalid_consent — semantic, deps-decidable, visible, and covered by property (d) like every other quarantine reason. Because the current command_status/3 callback sees only {cmd, args} and the consent check needs the op (author, causal position), the hook is a new optional module callback — op-aware, defaulting to :ok — consulted inside validate_command. That callback is the only substrate code this ADR adds.

§3

Dispositions & Adversary Tax

DISP-1Consent in the body, not a signature field on the op

The consent signature is data inside the hashed content, following the succession-certificate / election-close precedent, promoted to a validity conjunct.

REJECTED (was Rev 1's decision): an op-struct co_sigs field excluded from the hash. Fatal against the real accept path — idempotent-by-id acceptance drops late-arriving signatures (C4) — and it would additionally cost a dump-format bump (:lattice_log_dump_v1), a carrier wire change, and a TS codec change. The repo shape costs none of these.
TAX: the ceremony is ordered — consent must exist before the op can. The log therefore proves consent preceded append, and Rev 1's "cannot prove signing order" tax inverts into a small guarantee. Disclosed cost: the recipient signs a payload describing a transfer that does not yet exist as an op; the request-id binding (DISP-3) is what keeps that safe. A1/A2/A3: neutral.
DISP-2Consent is not authority — cap_ok and authority_ok untouched

The transfer's author must independently clear the existing cap_ok + authority_ok gates as the validated holder at the op's causal position. The consent conjunct is additive; the recipient's signature confers nothing, and no delegation, revocation, or holder-timeline code changes.

TAX: A2 strengthened — no self-serve custody, no consent-as-backdoor-authority. Disclosed cost unchanged from Rev 1: a dead or unresponsive holder cannot author a transfer; recovery of a tool from a vanished neighbor flows through the steward role and the existing succession machinery (ADR-0004), on purpose.
DISP-3Invalid consent is semantic quarantine — visible, reasoned, property-(d) covered

Rev 1 claimed malformed transfers should be "rejected pre-integration, invisible." That was wrong against design invariant 4 — nothing is dropped — and Rev 2 corrects it: a transfer with missing/invalid consent is a well-formed op that fails a semantic rule, so it quarantines with a reason and an audit event like :stale_holder or :double_transfer do today. Deps-decidable: the check is a pure function of the op bytes plus the causal presence of request_op_id.

REJECTED: structural-tier rejection in Log.accept — consent validity depends on the DAG (the request op's causal presence), which is precisely what the structural tier is documented not to decide.
TAX: a forged or coerced-looking transfer attempt is on the record — quarantined, reasoned, auditable. For the legibility corner this is the point: the failed attempt is evidence. A1 note: it is also a receipt of the attempt, which is fine for custody and must stay fenced from vouch-shaped surfaces (DISP-5).
DISP-4Determinism inherited; the strict-verify pin becomes a guarded invariant

Consent bytes sit inside the canonical body, so property (c) covers them with no new mechanism — provided signature bytes are deterministic and verification strictness matches across realms. Both are already true in main: RFC 8032 deterministic Ed25519 signing on both sides, OpenSSL strict verify on BEAM, { zip215: false } explicit in the TS client. This ADR promotes that from happenstance to invariant: any new verify site must pass the strict flag, enforced by V-07.

TAX: the PQC tripwire (gap D-A1) is sharper in Rev 2, not softer: with consent bytes inside the hash, a randomized-signature scheme (Dilithium) would make the op id itself nondeterministic per signing. Any Q-02 primitive swap must re-derive the entire property-(c) claim for consent-carrying commands — written here so the agility ADR inherits it.
DISP-5Generalized as a domain-tag registry + one optional callback; consumed narrowly

The mechanism is: a versioned consent domain tag, a payload schema, and the op-aware module callback. Rev 2 registers exactly one domain — lattice-custody-consent-v1 — and one command. UnanimousBoxesV1 demonstrates the multi-signer generalization already works at the app layer; ADR-MANDATE-01's dual-gate remains the named prospective beneficiary and adopts this via its own addendum or not at all.

TAX: unchanged live wire — every consent signature is a receipt by design. Correct for custody and treasury; any proposal to point this at vouch-shaped surfaces loses by default to the M4 findings — which main has since made concrete: the election work falsified the drop-in attestation swap and lives as a separate protocol precisely because coercion-facing signals cannot ride legible machinery like this.
§4

Verification — Falsify the Paper

V-05
One hook, one predicate — still

The consent conjunct lives inside validate_command's dispatch in Lattice.Authority and nowhere else on the BEAM side. Grep-enforced: no consent verification in Log, Sync, Materializer, or app modules outside the declared callback.

V-06
Cross-language quarantine parity — the sharpest risk in Rev 2

The TS client independently reimplements semantic reduction (clients/lattice-client/src/authority.ts). The consent conjunct must land there in lockstep or property (d) diverges by realm type — a BEAM realm and a phone disagreeing about a quarantine set. Gate: a custody-consent reference vector added to the conformance harness (mix lattice.export_vectors) covering valid consent, missing consent, invalid signer, wrong request id, and replayed consent — green on both implementations.

V-07
Strict-verify pin is a regression guard

Property (c) extended over consent-carrying commands: same seed ⇒ byte-identical logs including consent bytes. Plus a static check that every ed25519.verify call in the TS client passes { zip215: false } — the pin exists today at both sites; this test is what notices the third site that forgets.

V-08
Ceremony window races authority churn

Extend the V-04 generators: holder transfer/revocation scheduled between the request op, the consent signing, and the transfer append. Assert the existing authority_ok timeline check quarantines a transfer whose author lost holdership in its own causal past — the window must add no loophole the timeline machinery doesn't already close.

V-09
Replay is dead by request-id binding

Property test: a consent signature extracted from one integrated transfer, replayed inside a second transfer op (same parties, different request id — and same request id, second transfer), quarantines as :invalid_consent in every realm. This is the test DISP-1's disclosed cost hangs on.

V-10
The request surface carries refusal evidence — demonstrated, not asserted

Scenario test of the PD-003 dispute story on the existing inbox mechanism: an unresolved {:request, "custody", ...} is visible and timestamped in the analyzer's requests output and the read model; a refused one shows the holder's refusal op.

§5

Scope Fence

  • Op-struct signature fields — Rev 1's shape, rejected by C4. Do not reintroduce co-signatures outside the hashed content in any form. → ∅ · rejected by evidence
  • n-of-m threshold consent — the payload schema names one consenting signer. Quorum semantics (any 2 of 5 stewards) are a different validity question with partition edge cases; UnanimousBoxesV1-style unanimity at the app layer is the interim pattern if ever needed. → own ADR, on a real consumer
  • Signature aggregation (BLS-class) — one extra Ed25519 sig costs 64 bytes inside a body; nobody is short of them. → ∅ until compaction-scale evidence (ADR-0006)
  • Proximity binding of the ceremony — the QR/NFC exchange proves nothing cryptographic about physical presence and this ADR claims nothing. Lattice.Proximity remains unregistered; note the seam-naming caution below given the Attestation seam's history. → stubbed at app layer · own ADR on evidence
  • Blind or deniable consent — a consent that can't be shown is the election protocol's problem space, and main now proves that path needs its own multi-role machinery. This mechanism is the legible corner and must not grow toward the other one. → Township.Election lineage, if ever
  • Cross-replica atomic consented transactions — one op, one replica, one command. Multi-replica atomicity is consensus-shaped and the substrate deliberately does not have it. → questioned before built
  • Registering Mandate commands — named beneficiary, not a consumer. → ADR-MANDATE-01 addendum
Honesty caveats — read before believing the ADR

Rev 2's load-bearing risk moved: it is no longer "the paper doesn't match the repo" (it now does, at main @ a96b3c4) but the dual-implementation seam — semantic reduction exists twice, in Elixir and TypeScript, and the consent conjunct must ship in both with a conformance vector or property (d) fails silently across realm types; V-06 is the gate that matters most. The optional op-aware callback is a real (if small) change to the Authority behaviour surface and should be reviewed against every existing replica module, not just Township.Matter. The consent payload schema (five fields, one domain tag) is deliberately minimal; anything anyone wants to add to it — timestamps, terms, due-backs — belongs in the command args or the Cap caveats, not the signed consent, or the schema starts accreting. Reconciliation was against main, which has merged past the older working branch; if PD-003 work lands on a feature branch, re-run the greps there before trusting line references. And the Attestation seam's history is this ADR's cautionary tale: a behaviour named before its research verdict had to be frozen and routed around — which is why Lattice.Proximity stays an unregistered name in a fence, not a stub in the tree, until there is evidence.
