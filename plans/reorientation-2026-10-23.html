What the system is

Every change anyone makes is a signed operation. Operations link to their causal predecessors by hash, forming a DAG. A Replica is a schema written in a small DSL. Each field either merges as a CRDT (:lww, :or_set, :causal_list) or is an authority field that names who holds a role. Whether an operation counts is decided by replaying the log through the authority judge. The judge checks delegations, capability attenuation, leases, revocations and succession. Operations without valid authority are quarantined with a named reason, never silently dropped. Two peers holding the same operations materialize byte-identical state.

Transport is separate from authority. The carrier moves already-signed operations over WebSocket: frontier exchange, pull of missing operations, an opt-in relay that persists before it acknowledges, and an ops_available hint that triggers a pull. The relay server holds no participant keys and does not decide authority. It can read plaintext and can withhold service, and the copy rule D1 requires every hosting sentence to say so.

Built vs. attempted, by evidence tier

What a focus session looks like

Pick the session type before you start. Most of what blocks progress now needs a decision session, not a build session.

Decision session · 60–90 min, no code

Read one plan section, decide its open OD/row questions, and write each answer as a one-line dated decision in the index or a decisions record. Claude drafts the options and a recommendation; you choose.

Build session · one index row

Take one row from RED test to merged PR. Claude implements and you review and steer. One row per session; anything else that comes up goes in its own row.

  1. Orient (10 min)

    See what is in flight before touching anything. Other sessions may share this checkout.

    git status --short --branch
git worktree list
gh pr list
gh run list --branch main --event push --limit 1

    Then read the Working policy at the top of plans/README.md and the status cell of the row you plan to take.

  2. Prepare the toolchain (first session only)

    Use asdf's mix. The mix on PATH is a broken mise shim, and Homebrew Erlang leaks into child VMs.

    export PATH="$HOME/.asdf/installs/erlang/28.3.1/bin:$HOME/.asdf/installs/elixir/1.19.5-otp-28/bin:$PATH"
npm --prefix clients/lattice-client ci && npm --prefix clients/lattice-client run build
npm --prefix clients/treehouse-tauri-shell ci
~/.asdf/shims/mix check

  3. Touch the real thing (15 min)

    Run a narrated demo, so the session starts from behaviour rather than prose.

    ~/.asdf/shims/mix run scripts/treehouse_demo.exs
~/.asdf/shims/mix run scripts/township_demo.exs

  4. Pick exactly one row

    Read its plan file in full. Note its STOP conditions and the evidence tier it can claim. Tell Claude something like "focus session: row 248".

  5. Work loop

    • Write a failing test that shows the behaviour (RED), then implement until it passes (GREEN).
    • Run ~/.asdf/shims/mix check, plus, if TS in clients/lattice-client changed, npm --prefix clients/lattice-client run build, run typecheck and the named gate scripts for the area you touched (for example run conformance, run canonical, run treehouse). That package has no aggregate npm test.
    • Get one adversarial review (Codex Sol 6.1 high). Add a second only for authority, canonical, carrier, custody or workflow diffs. If a third round finds the same class of issue, treat it as a design question for you.
    • Open the PR, claiming exactly one evidence tier. The exact-tip hosted run is the gate.

  6. Close out (10 min)

    Update the row's status cell (one line, ≤200 characters). Evidence goes in the PR description, not the plan. File new findings as new rows; don't fix them in passing. Record a memory note for anything the next session must know.
